# go-lintjson

校验 JSON，并且把错误位置说清楚。

标准库报错只给一个字节偏移：

```
invalid character '}' looking for beginning of object key string
```

面对几百行的配置文件，还得自己数到第 431 个字节去，而且这句话也很难让人
反应过来"哦是多打了个逗号"。这个工具直接告诉你在第几行第几列、
那一行长什么样、以及大概率是哪里写错了。

```powershell
go run . config.json
```

```
config.json:3:16: 对象里多了一个逗号（最后一项后面不能有逗号）
    "port": 8080,,
                 ^
```

## 用法

```powershell
go run . a.json b.json        # 校验多个文件
cat a.json | go run .         # 从管道读
go run . -fmt a.json          # 格式化后输出到屏幕
go run . -fmt -w a.json       # 直接写回文件
go run . -fmt -indent "" a.json   # 压缩成一行
go run . -q a.json            # 只看退出码，不输出
go run . -no-dup-check a.json # 跳过重复键检查
```

退出码：`0` 没问题，`1` 发现问题。适合放进 CI 或 git 钩子。

## 能认出来的错误

| 你写的 | 提示 |
| --- | --- |
| `{"a": 1,}` | 对象里多了一个逗号 |
| `[1, 2,]` | 数组里多了一个逗号 |
| `{'a': 1}` | 键名要用双引号，JSON 不支持单引号 |
| `{"a": None}` | None 是 Python 写法，JSON 要用 null |
| `// 注释` | JSON 不支持注释 |
| `{"a":1 "b":2}` | 两个键值对之间少了逗号 |
| `{"a": 1` | 内容不完整，可能有括号或引号没闭合 |
| `{} {}` | 顶层已经是一个完整的值了，后面多出了内容 |

## 重复键检查

这个是标准库完全不管的：

```json
{
  "port": 8080,
  "port": 9090
}
```

`encoding/json` 解析这段**不报任何错**，静默地让后面的覆盖前面的。
配置文件里这个坑很阴——你改了上面那个 `port`，跑起来生效的却是下面那个，
怎么调都不对。

```
config.json:3:3: 键 "port" 重复了（第 2 行已经出现过），后面的会覆盖前面的
    "port": 9090
    ^
```

不同层级、或者数组里各元素的同名键是合法的，不会误报。

## 几个细节

**列号按字符算，不按字节**

一个汉字 3 字节。按字节报列的话，含中文的行报出来的列号会大得离谱，
跟编辑器里看到的对不上。

**`^` 会对齐**

tab 缩进保持 tab（用空格填充的话，tab 显示成 4 格或 8 格宽，`^` 就跑偏了）；
汉字按两列宽计算。

**BOM 不会让它发疯**

Windows 上记事本、PowerShell 的 `Set-Content` 存出来的 UTF-8 都带 BOM。
标准库不认，会指着一个看起来完全正常的 `{` 说"这里应该是一个值"——
这种报错最坑，肉眼根本看不出问题在哪。这里会自动剥掉。

**空文件说人话**

标准库对空输入报 "unexpected end of JSON input"，看着像文件被截断了，
其实是压根没内容。这里直接说"文件是空的"。

**`-w` 是原子写**

先写临时文件再 rename。格式化到一半出错不会把你的原文件毁掉。
